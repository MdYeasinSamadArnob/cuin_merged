# Doris SQL Compatibility Matrix

> **Note (2026-08-04):** DuckDB has since been removed as a pipeline engine entirely -- Apache Doris is now the sole execution engine. This document is retained as a historical record of the original DuckDB-to-Doris compatibility probe; it is not re-run or updated going forward.

Generated by `backend/tools/doris_probe.py` against a live Doris instance.
`SELECT VERSION()` reported: `5.7.99` (Doris reports a MySQL-protocol-compatible version string, not its own release number -- the container image tag is the source of truth for the actual Doris version).

## Environment notes

The Doris BE (storage/compute node) refuses to start unless:
- Host kernel `vm.max_map_count >= 2000000` (`sysctl -w vm.max_map_count=2000000`)
- Swap is disabled, OR the BE is launched with `SKIP_CHECK_ULIMIT=true` in its environment

Both are standard, documented Doris production requirements (not specific to this probe) -- provision them via a host sysctl / init container in any real deployment.

## Physical design: colocate join, verified live (Phase 8)

`backend/engine/ports/doris_ddl.py` distributes `identifiers` by `HASH(id_type, value_norm)` -- the exact key `deterministic_blocker`'s EXACT_IDENTIFIER self-join uses. `backend/tests/integration/test_doris_colocate_plan.py` creates that table on a live instance, inserts a 500-row block sharing one mobile value, and runs `EXPLAIN` on the self-join. Actual plan output (Doris 4.0.3, single-BE sandbox):

```
HAS_COLO_PLAN_NODE: true
2:VHASH JOIN(268)
|  join op: INNER JOIN(COLOCATE[])[]
|  equal join conjunct: (id_type[#18] = id_type[#8])
|  equal join conjunct: (value_norm[#19] = value_norm[#9])
```

No `SHUFFLE` appears anywhere in the plan. This is the central performance claim of the migration plan (colocated bucketing turns the blocking self-join into a local, no-network-shuffle operation) confirmed against a real query planner, not asserted from documentation.

Session variables actually available on Doris 4.0.3 differ from the plan's first draft -- corrected in `doris_ddl.py`:
- There is **no** `enable_colocate_join` variable. Colocate planning is **on by default** (`disable_colocate_plan` defaults to `false`).
- `runtime_filter_type`'s value is a comma-list using the token `IN_OR_BLOOM_FILTER`, not `IN_OR_BLOOM` (default: `IN_OR_BLOOM_FILTER,MIN_MAX`).
- `enable_spill` and `parallel_pipeline_task_num` exist exactly as planned.

## Environment setup used to reach a queryable state (this session)

Beyond the two documented BE preconditions above, this sandbox additionally needed, because it is a single-BE, swap-enabled host:
- `ADMIN SET FRONTEND CONFIG ("force_olap_table_replication_num" = "1")` -- a fresh Doris FE defaults new tables to `replication_num=3`, which a single-BE cluster can never satisfy. Not needed on a real multi-BE deployment.
- The BE was started with `SKIP_CHECK_ULIMIT=true` rather than actually disabling host swap, since that's a sandbox-only constraint.
- The all-in-one container's entrypoint script backgrounds the FE/BE Java processes and then `exec`s its (empty) `CMD`, which exits the container immediately if no `CMD` is supplied -- run it as `docker run ... apache/doris:4.0.3-all-slim tail -f /dev/null` to keep the container alive after Doris starts.
- Stream Load's normal flow (PUT to FE, 307 redirect to the target BE's own HTTP port) needs the BE's HTTP port reachable directly from the client, not just proxied through the FE -- map it explicitly (`-p 8040:8040` alongside the FE's `-p 8130:8030`), and don't rely on an HTTP client's automatic redirect-following: it strips `Authorization` on any redirect that changes host or port (correct, deliberate behavior, not a bug), so Stream Load clients should issue the follow-up PUT to the redirect `Location` as an independent request with their own auth header, not trust automatic redirect handling.
- A fresh Doris FE defaults new OLAP tables to `replication_num=3`; a single-BE sandbox can never satisfy that. `ADMIN SET FRONTEND CONFIG ("force_olap_table_replication_num" = "1")` overrides it cluster-wide for a single-BE deployment.

## Full-scale finding: Stream Load's JSON parser mis-handles embedded control characters

Found only at full 1.5M-row scale (never surfaced on the 5k-row sample fixture -- worth remembering when deciding how much of a dataset to validate against before trusting a migration "done"): a source `DOCUMENT` field value containing a stray trailing `\r` (real-world data noise, not something CUIN put there) round-trips correctly through DuckDB's `COPY ... TO 'x.json' (FORMAT JSON)` -- properly JSON-escaped as the two bytes `\` `r`. Doris's Stream Load JSON parser (`format:json`) does not correctly unescape that sequence back into a carriage-return byte; it comes out the other side as a literal lowercase `r` character appended to the value. That corrupted value then fails TIN validation (`^[0-9]{12}$`, now 13 characters), where the DuckDB path -- which reads Parquet directly and never round-trips through JSON at all -- retains a clean value and validates correctly. Net effect: exactly 1 candidate pair out of 549,879 differed between engines on the full dataset, traced to this one record.

**Fix applied** (`engine/ports/doris_ingest.py::export_parquet_to_ndjson`): strip `\r`/`\n`/`\t` from every string and array-of-string field during the Parquet -> NDJSON export step, before the data ever reaches Doris's JSON parser. Control characters are never meaningful content in any of these fields (name, mobile, email, document, address), so this is a safe, narrowly-scoped fix at the ingestion boundary -- it does not touch the DuckDB code path at all (DuckDB never uses this export function). After the fix, both engines produce byte-identical candidate pairs on the full dataset -- see `tests/integration/test_doris_orchestrator_parity.py` for the automated version of this check (currently run against the 5k sample for speed; the full-dataset comparison here was done manually during migration and is recorded for posterity, not re-run on every test invocation).

## Reading Parquet in place: the `LOCAL()` table-value function (lakehouse migration, Phase 1.2)

Doris 4.0.3 confirmed present: `LOCAL()`, `S3()`, `HDFS()` TVFs, plus `CREATE CATALOG ... PROPERTIES('type'='hms'/'iceberg')` for Hive/Iceberg external catalogs. `LOCAL()` is what a single-BE, low-resource deployment needs -- no object store, no catalog service.

Two live-verified behaviors, neither documented anywhere obvious beforehand:

1. **`file_path` is resolved relative to the BE process's own working directory (`$DORIS_HOME/be/`), not the container filesystem root -- even when the value starts with `/`.** `LOCAL('file_path' = '/tmp/x/*.parquet', ...)` against a file that genuinely exists at container path `/tmp/x/` fails with `failed to glob /opt/apache-doris/be//tmp/x/*.parquet: No matches found` -- Doris silently prefixes the BE home directory onto whatever string you pass. The file has to live under `$DORIS_HOME/be/` (a bind mount in `infra/docker-compose.yml`'s `doris` service, mounted at the SAME relative subpath name the `backend` service uses from its own working directory -- e.g. `data_source/oracle_data.parquet/...` resolves identically on both sides).
2. **A bare directory resolves zero files.** `LOCAL('file_path' = 'data_source/oracle_data.parquet', ...)` (no glob suffix) against a directory containing 12 valid `part-*.parquet` files returns `No matches found`. The explicit glob `data_source/oracle_data.parquet/*.parquet` is required -- unlike DuckDB's `read_parquet()`, which transparently globs a directory argument.

Verified live end-to-end through `DorisPipelineOrchestrator._stage_ingest` (not just a raw SQL probe): `CREATE OR REPLACE VIEW raw AS SELECT * FROM LOCAL(...)` reads all 1,567,782 rows of the full dataset with zero copy into a Doris table, `information_schema.tables` confirms `raw` is a `VIEW` not a `TABLE`, and case-insensitive uppercase column references (`SELECT CUSTOMER_CODE, NAME FROM raw`) resolve correctly against the Parquet file's actual lowercase column names -- Doris follows the same unquoted-identifier case-insensitivity as DuckDB, so none of `engine.normalize.explode_dialect`'s uppercase field references needed changing.

`get_single_backend_id()` (`engine/ports/doris_ingest.py`) refuses to guess when `SHOW BACKENDS` returns more than one row -- `LOCAL()` can only ever be correct for a single-BE cluster, since it reads a specific BE's own local disk. A multi-BE deployment needs the lake on shared storage instead (`S3()` TVF or an external catalog), which is a deployment-shape decision, not something to silently paper over with a fallback.
